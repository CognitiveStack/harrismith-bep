### Slide 1 — A CDE is a governed process, not a folder tree · 1.5 min

**Purpose of the slide**

Establish the CDE as an **information-management process supported by
technology**, and separate the process from the folders and permissions that
implement part of it.

**The sourced statement that carries the slide**

> The CDE is **an information-management process supported by technology**. It is
> not a folder tree. A folder structure is one way of implementing part of the
> process; it is not the process, and reorganising folders does not change how
> information is governed.

*(`S1` §6.1 — **Harrismith project wording, quotable. Not an ISO definition.**)*

`S2`'s own purpose statement says it independently: *"**The CDE is a process, not
a folder tree.** A folder structure implements part of the process… the presence
or absence of a folder proves nothing about state."*

**What the CDE controls**

| # | | |
|---|---|---|
| 1 | **How information is developed** | Authoring, iteration and internal checking, under task-team control |
| 2 | **How it is checked** | Against a defined checking requirement |
| 3 | **How it is shared** | Deliberately, for an identified purpose, after check and authorisation |
| 4 | **How it is authorised** | As a separate decision, by a function that holds the authority |
| 5 | **How it is delivered** | As an act with a recipient and a purpose |
| 6 | **How it is retained** | Traceably, by an approved retention method |

*(**Supported interpretation**, built from `S1` §6.1's principles and `S2` §1.
No source lists these six — `M4-S1-04`.)*

**Four distinctions**

| # | Distinction | Source |
|---|---|---|
| 1 | **Technology supports the process** | `S1` §6.1 — *"supported by technology"* |
| 2 | **A folder tree may implement part of the arrangement** | `S3` §3 adopts four areas **and maps them to states** — the mapping is the governance, not the folder |
| 3 | **A folder tree alone defines no authority or permitted use** | **`CGD-C01`** — *"The existence or name of an area does not by itself establish an information state"* |
| 4 | **Permissions create no professional or governance authority** | `S1` §6.9; `S2` §14 — *"Permission ≠ authority"* |

**And the implementation caution**

> **Platform access does not prove the process is operating correctly.**

`S4` §9 puts it at its sharpest: *"Platform permissions, sender identity, review
participation and the ability to create a Transmittal are **not** governance
authority. **Being able to perform an action in the software says nothing about
who was authorised to decide it.**"*

**Connection to earlier modules — four lines, then move on**

```text
Module 1 — the BEP records the agreed method
Module 2 — functions and authorities are assigned
Module 3 — principles become project-specific governance and configuration
Module 4 — the workflow and state controls, examined in detail
```

**Roughly fifteen seconds.** **Do not re-teach any of them.** If the audience
did not attend, the four lines still work as orientation.

**Required message**

> The CDE is the governed process; the platform and folders are tools used to
> implement it.

*(**Teaching synthesis**, consistent with `S1` §6.1 and `S2`'s purpose statement
— `M4-S1-09`.)*

**Governance and implementation status**

| | |
|---|---|
| CDE principles (`S1` §6.1) | **`CONTROLLED GOVERNANCE`** |
| The workflow that implements them (`S2`) | **`PROPOSED GOVERNANCE`** |
| Four-area root topology (`S3` §2) | Adopted — **`IMPLEMENTATION UNVERIFIED`** (`CGD-C07`) |

**Say the second row.** `S2` classifies its own workflow as proposed and states
it **does not describe the live platform**.

### Slide 2 — State, version, revision, status and suitability are different · 1.5 min

**Purpose of the slide**

Stop the audience treating every change-related property as interchangeable.
This is the module's vocabulary slide, and Sections B and C depend on it.

**The five properties — controlled Harrismith wording**

| Property | Wording | The question it answers |
|---|---|---|
| **State** | *"WIP / Shared / Published / Record"* — the governed information-use context | **Where may it be used?** |
| **Version** | *"A platform or file history instance"* | **Which stored occurrence is this?** |
| **Revision** | *"A controlled issue identifier, **where project convention requires one**"* | **Which managed issue is this?** |
| **Status** | *"A workflow or decision condition"* | **What condition is declared?** |
| **Suitability** | *"What the information may be used for"* | **For what use is it suitable?** |

*(`S1` §6.8, with `S2` §13. **Harrismith project wording — not ISO definitions.**
The five questions are the presenter's framing — `M4-S2-07`.)*

**Note the conditional in *revision*.** *Where project convention requires one* —
and **no project naming or revision convention has been established** (`S1`
§11.3; `S12`). The property is defined; **its code set is not**.

**The rule, stated by both sources**

> **These are never used interchangeably.** — `S2` §13
>
> **A new platform version creates none of the others.** Saving a new version
> does not by itself create a new revision, change the information state,
> constitute approval, or make the information suitable for a new purpose. **Each
> of those is a separate act with its own decision and its own responsible
> role.** — `S1` §6.8

**Six relationships**

| | |
|---|---|
| 1 | **A new version may exist without a new revision** |
| 2 | **A revision change does not itself authorise a state transition** |
| 3 | **Status does not equal suitability** |
| 4 | **Suitability does not equal acceptance** — acceptance is a recipient decision against a stated purpose (`S2` §3) |
| 5 | **Folder location creates none of the five** — `CGD-C01` |
| 6 | Several may change together, **and they remain conceptually distinct** |

**And the second table `S2` §13 supplies, which does the same work downstream:**

| A **Published** container does **not** automatically mean |
|---|
| delivered · received · accepted · suitable for a different purpose |

**Required message**

> Five properties may describe the same container, but each answers a different
> governance question.

*(**Teaching synthesis** — `M4-S2-12`.)*

**What this slide must not do**

| Must not | Because |
|---|---|
| Arrange the five as a maturity sequence | They are not stages. A container has all five at once |
| Use arrows implying automatic progression | **`S1` §6.8: a new version creates none of the others** |
| Apply or invent a revision code set | **None is established** (`S1` §11.3) |
| Apply or invent a suitability code set | **None is established** |
| Claim these are ISO definitions | They are this project's wording |

### Slide 3 — The Harrismith information-state model · 1.5 min

**Purpose of the slide**

Introduce the project's four states and the purpose of each — **without yet
teaching transitions**. Transitions are Section C.

**The four states — verified controlled labels**

| State | Controlled definition | Who may rely on it |
|---|---|---|
| **WIP** | *"Information under originator / task-team control. **Not authorised for general project reliance.**"* | The originating task team only |
| **Shared** | *"Information made available beyond the originating task team for an identified purpose, **after required checking and authorisation**."* | Receiving teams, **for the stated purpose** |
| **Published / Authorised** | *"Information authorised for a defined delivery or use purpose."* | Whoever the authorised purpose identifies |
| **Record / Retained** | *"Historical evidence retained for traceability, according to the project's retention approach."* | Anyone needing traceability |

*(`S1` §6.3 — **the governing definition**. `S2` §1 elaborates each.)*

**A terminology note, recorded rather than smoothed over**

**Four label forms exist across the controlled sources** for the fourth state —
`Record / Retained` (10 occurrences), `Record / retained` (1, in the governing
`S1` §6.3 table), and the short forms `Published / Record` and `Published /
retained`. **No source declares them formal synonyms.**

**They differ in casing and abbreviation, not in meaning.** Teach the majority
form; note that the governing definition uses lower-case *retained*. **Do not
present either as *the* correct label** — see
[`source-inventory.md`](source-inventory.md) §6.

**Seven mandatory distinctions**

| # | | Source |
|---|---|---|
| 1 | **WIP is not yet authorised for broader reliance** — *"visibility of WIP is not permission to rely on it"* | `S1` §7.5; `S2` §1 |
| 2 | **Shared supports controlled use for a defined purpose** | `S1` §6.3 |
| 3 | **Shared does not equal Published** — *"Shared does not mean published, accepted, or suitable for every purpose"* | `S2` §1 |
| 4 | **Published requires separate authority** — and *"Published does not mean universally suitable, forever final, or automatically accepted"* | `S2` §1; `S1` §6.7 |
| 5 | **Record / Retained is not automatically a folder** | `S1` §6.3; `S2` §1; **`CGD-C06`** |
| 6 | **A state is not created by moving a file** | **`CGD-C01`, `CGD-C03`** |
| 7 | **State does not prove delivery, receipt or acceptance** — those are events, actions and statuses, **not states** | `S2` §3, §13 |

**The four areas, and what they are not**

`S3` §2 adopts four root areas — **`0. Common Files`**, **`01. WIP (Work in
Progress)`**, **`02. Shared`**, **`03. Published`** — and §3 maps three of them to
states.

| | |
|---|---|
| **`0. Common Files` is an area, not a state** | *"Nothing becomes approved, controlled or relied upon by being placed in it"* |
| **`02. Shared`** | *"Placement alone does not evidence that checking or authorisation occurred"* |
| **`03. Published`** | ***"Putting a file in `03. Published` does not publish it.** Publication is a chain of governed events, not a location"* |
| **Record / Retained** | **No root folder.** *"No mandatory `04 Archive` root is approved or required"* |

**The state diagram — and what it may not show**

```text
WIP
  →  Shared                    T1 · authorising function ESTABLISHED
  ⇢  Published / Authorised    T4 · BLOCKED — authority UNRESOLVED
  ⇢  Record / Retained         conceptual state; retention approach TBD
```

**Verified from `S2` §3.** `T1`'s authorising function is the **Task-Team Lead**
(`S1` §9.4) — the connector may be solid. **`T4` has no available authorising
function; information remains Shared** — the connector must be broken.

**Mandatory warning, on the slide:**

> ### `Conceptual state model — not proof of live platform implementation`

**Required message**

> Each state defines a different permitted purpose; movement between them
> requires more than technical file movement.

*(**Teaching synthesis**, consistent with `CGD-C01` and `CGD-C03` —
`M4-S3-14`.)*

**Governance and implementation status**

| Element | Governance | Implementation |
|---|---|---|
| The four state concepts | **`CONTROLLED GOVERNANCE`** (`S1` §6.3) | — |
| Four-area root topology | Adopted (`S3` §2) | **`IMPLEMENTATION UNVERIFIED`** |
| `WIP → Shared` | **`CONTROLLED GOVERNANCE`** — authority established | **`IMPLEMENTATION UNVERIFIED`** — only Architecture demonstrable (`S4` §7) |
| `Shared → Published` | **`BLOCKED`** | Not reached |
| Record / Retained | **`UNRESOLVED`** — retention approach TBD | No folder; none required |

### Slide 4 — Work in Progress: authoring inside the task team · 1.0 min

**Purpose of the slide**

Explain WIP as the **controlled working context** in which the originating task
team develops and checks its own information — before any controlled sharing.

**What WIP is**

> *"WIP is the task team's **working state**."* It includes drafting and
> modelling, internal iterations, local coordination within the team, correction,
> and checking preparation. *(`S1` §7.5)*

> *"Information under originator / task-team control. **Not authorised for
> general project reliance.**"* *(`S1` §6.3)*

**Seven points**

| # | | Source |
|---|---|---|
| 1 | It is the task team's **authoring and internal development context** | `S1` §7.5 |
| 2 | It remains **under the originating task team's responsibility** — authoring, internal checking, readiness assessment, authorisation for progression where governance assigns it | `S1` §6.4 |
| 3 | It may contain **incomplete, provisional or uncoordinated work** — *"WIP may contain many versions"* | `S1` §7.5 |
| 4 | It is **not authorised for broader project reliance** | `S1` §6.3, §7.5 |
| 5 | It undergoes **authoring and checking** activities | `S1` §6.4, §7.6 |
| 6 | **It does not become Shared because someone else can access it** | `S1` §7.5 |
| 7 | **It does not become Shared because it exists in a platform** | **`CGD-C01`, `CGD-C03`** |

**The sourced statement that carries the slide**

> **Visibility is not permission.** Being able to see or open another team's WIP —
> through folder access, a platform permission, or any other means — **does not
> constitute authority to use it. Permission to read is not authorisation to
> rely.**

*(`S1` §7.5 — **quotable verbatim**, and the strongest line available.)*

```text
Visible to someone
  ≠
authorised for that person's reliance
```

**And the corollary:** *"WIP versions are not project exchanges. A new version in
WIP is a working step, not a share, not an issue, and not an event that other
teams are expected to act on."* (`S1` §7.5)

**The responsibility boundary — named, not re-taught**

| Function | In WIP |
|---|---|
| **Author** | Authors |
| **Checker** | Checks |
| **Task-Team Lead** | May authorise the controlled `WIP → Shared` transition **where the approved governance establishes it** — `S1` §9.4 |
| **Everyone else** | Must not treat WIP as coordinated or approved information |

**Four lines. Module 2 holds the full role model** — do not re-teach it.

**One further caution, and it is Harrismith's own**

> *"A team space is a platform construct.** It is not an organisation, not a
> discipline, not a contractual appointment. **Membership confers no
> authority.**"* *(`S1` §6.4)*

**Harrismith implementation status — carefully**

| | |
|---|---|
| `ARC-01` | **One qualified observation** — *"Live equivalent observed"* (`S4` §7) |
| What it does **not** prove | **The complete WIP workflow.** It is a container observation, not a workflow demonstration |
| The other five containers | *"Not observed as a live direct coordination input at the inspected level"* |
| The standing caution | **"Absence of observation is not observation of absence"** (`S4` §7) |

**Do not label WIP as fully implemented.** Do not label it as failing either.

**Required message**

> WIP is where a task team develops its information — not where the wider project
> is entitled to rely on it.

*(**Teaching synthesis**, consistent with `S1` §6.3 and §7.5 — `M4-S4-14`.)*

**Boundary.** *That* a governed route out of WIP exists may be named. **How it
works is Slides 8–11.**

**The misconception the slide must refuse — visibly**

```text
Shared
  =
approved
```

> ### Shared means authorised for **a defined use**.
> ### It does not mean approved for **every** use.

>
> - the BIM Manager;
> - the BIM Coordinator;
> - the CDE Administrator;
> - the Architect.
>
> Until the delivery arrangement is approved, this authority remains **TBD**, and
> this document **says so rather than defaulting it to whichever role is
> nearest.**

**Why the field must not be omitted.** An omitted authority field implies **no
authority is required**. An empty one shows accurately that **authority is
required and unassigned**.

**And the platform caution, `S1` §9.7:** *"**Platform write permission is not
publication authority.** Being able to place a file in a published location is a
software capability, **not a decision anyone made**."*

**The mandatory blocked-transition treatment**

```text
Shared
  ⇢  Published / Authorised          BLOCKED
```

**Three labels, all required:**

| Label |
|---|
| **`T4 blocked`** |
| **`No available authorising function`** |
| **`Information remains Shared`** |

**Required message**

*(**Teaching synthesis**, consistent with `S1` §9.7 and `S2` §3 — `M4-S6-16`.)*
