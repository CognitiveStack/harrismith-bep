# Module 8 — Workshop Method Framework

**Status:** **`ARCHITECTURE BASELINE — T8-B PENDING CHATGPT GOVERNANCE
REVIEW`**

**`TEACHING METHOD — NOT GOVERNANCE`**

This framework defines the Module 8 teaching method for BEP decision
workshops. Every element below is one of four kinds, and says which:
**controlled-source support** (exact Harrismith citation) ·
**working-pattern support** (the expressly non-governing `working/` family —
`FOR REVIEW`, `Authority: None`, `Not approved`) · **teaching inference**
(a bounded generalisation from a source) · **teaching synthesis** (original
teaching construction). **No element is Triviron governance, and no actual
workshop exists, is scheduled, or is simulated here.**

---

## 1. The central three-phase model

`BEFORE → DURING → AFTER`

Classification: **`TEACHING SYNTHESIS — NOT A CURRENT HARRISMITH OR TRIVIRON
GOVERNANCE WORKFLOW`.** The phases package source-supported components into a
teachable shape; the packaging itself is synthesis.

## 2. BEFORE — preparation

| Step | Basis |
|---|---|
| 1. State the workshop purpose | Working-pattern (template "Purpose"; WP5) |
| 2. Select decision-backlog items | Teaching interpretation (Module 7 register as decision backlog) |
| 3. Identify evidence required | Teaching interpretation (register field 7; framework §2.3) |
| 4. Identify evidence available / missing | Teaching interpretation (register fields 8–9) — required vs available stays distinct |
| 5. Identify dependencies | Teaching interpretation (register field 16) |
| 6. Identify required authority type / functions | Teaching interpretation (schema §5 kind-only convention) + controlled support (BEP §9.2 — different decisions, different functions) |
| 7. Prepare a decision agenda | **Teaching synthesis**, using the bounded controlled analogue (`Publication-Planning-Control-Framework` §1.3 — *"an agenda of decisions, their evidence requirements, and their boundaries"*). Generalising that publication-planning device to workshops generally is **inference**; the workshop artefact itself is synthesis |

**The decision agenda is a teaching artefact concept.** It may conceptually
carry, per matter: decision question · evidence required · evidence
available / missing · dependencies · required authority · current status ·
controlled destination. It is **not a decision, not an approval record, and
not an established Triviron artefact** — and no agenda ID, template name or
Triviron document is invented for it.

## 3. DURING — facilitation

| Step | Basis |
|---|---|
| 1. Present classified evidence | Working-pattern (template: evidence with its classification per item) |
| 2. Frame the decision question | Working-pattern (template "Decision required? … what decision, and which function") |
| 3. Discuss options | Working-pattern (template "Options discussed") |
| 4. Preserve **option ≠ decision** | Working-pattern, verbatim: *"Options are not decisions"* |
| 5. Preserve **proposal ≠ approval** | Working-pattern, verbatim: *"A proposal is not an approval"*; controlled support in WP-cited BEP §12.5–§12.7 |
| 6. Check whether the required authority is actually established / engaged | Teaching inference from schema §5 + BEP §9.2; see the authority checkpoint below |
| 7. Distinguish the possible outputs | Working-pattern (WP2/WP6 types and routes): clarification · evidence request · action · proposal · decision required · unresolved / deferred matter · **authorised decision only through the appropriate governed route** |
| 8. Record the outcome in the correct record | Controlled support (BEP §8.9; register practice) + working-pattern (WP10 channels — each record holds its own part) |
| 9. Do not convert unsupported discussion into governance | Controlled support (BEP §8.9) + STOP `M8-S04`, `M8-S10` |

**One decision conversation at a time** is **teaching inference** from the
one-matter-per-row discipline of the controlled agenda analogue and the
register; no source states it for meetings.

## 4. The authority checkpoint

**A useful discussion can occur without decision authority. A governed
decision cannot be claimed merely because the discussion occurred.**

Classification: **`TEACHING SYNTHESIS` grounded in controlled/working source
distinctions** — BEP §8.9 (meetings support decisions; a discussion is not a
record), WP1 (*contribution rights are not governance authority*), WP5 (*a
workshop is not a parallel decision authority*).

**If the required authority is not established or engaged, the workshop may
still produce:** reasoning · evidence requests · proposals · actions · a
recognised decision requirement. **It must not invent an authorised
decision** — and no simulated authority is created to fill the gap
(`M8-S02`, `M8-S03`, `M8-S11`).

## 5. AFTER — follow-up

| Step | Basis |
|---|---|
| 1. Reconcile the workshop/working record | Working-pattern (template; WP11) |
| 2. Record consequential governed decisions in the appropriate controlled governance record | Controlled support (BEP §8.9; Governance & Decision Register practice; WP6 — the authoritative decision belongs there *"and nowhere else"*) |
| 3. Distinguish **decision ≠ implementation** | Controlled support (BEP §12.8; WP8 — *"A decision made is not a change completed"*) |
| 4. Identify affected controlled artefacts | Working-pattern (WP7) |
| 5. Permit updates only through the authorised implementation route | Controlled support (BEP §12.7–§12.8; WP7 — an approved working proposal authorises no external change) |
| 6. Preserve unresolved matters / typed absence | Teaching interpretation (Module 7 Slide 13 vocabulary; UD-001 practice) |
| 7. Assign evidence or action follow-up where supported | Working-pattern (template actions — owning function; **no due-date convention exists and none is invented**) |
| 8. Verify implementation where required | Controlled support (BEP §12.9; WP8) |
| 9. Retain traceability | Controlled support (register subsequent-status practice; WP10 — *"a decision nobody can produce afterwards did not happen"*) |

**No automatic route exists: `workshop → BEP edit`.** The safe conceptual
route is:

```text
workshop discussion / working record
   │  where governance significance exists
   ▼
governed decision route
   ▼
controlled decision record
   │  where authorised
   ▼
controlled implementation
   ▼
verification / traceability
```

## 6. Boundaries carried by this framework

- **Working Process boundary.** The Working Process and workshop template are
  the principal workshop-adjacent worked pattern, always cited with
  `FOR REVIEW · Authority: None · Not approved`. **The Working Process is
  useful because it demonstrates separation between participation and
  governance; it is not authoritative workshop governance** — and it is never
  called an approved process, a project workshop procedure, a Triviron
  procedure or a project requirement.
- **Meeting / decision boundary.** Controlled support, carried accurately and
  not overextended: within the Harrismith training implementation, meetings
  support decisions; discussion itself is not the controlled record;
  decisions of consequence belong in the appropriate controlled record (BEP
  §8.9). The teaching sentence **"Participation in a meeting does not by
  itself create decision authority"** is used only as **labelled synthesis**
  of that principle.
- **Minutes / governance boundary.** No controlled `minutes` construct
  exists; the word is used only as a generic teaching concept. The sentence
  **"Minutes record that a conversation occurred; governance records what was
  decided, by whom, under what authority and with what status"** is
  **`TEACHING SYNTHESIS — SOURCE-SUPPORTED IN COMPONENTS`**, never quoted
  governance. Minutes may form part of evidence; the prohibition is that they
  are not **automatically** approval or authoritative decision evidence
  merely because they exist (`M8-S05`).
- **Closure boundary.** Contribution-level closure logic exists (WP8); **no
  governed workshop-level closure criterion exists** — the module teaches
  *conclude and follow up*, and any closure model beyond that is labelled
  synthesis.
- **Evidence boundary.** All Triviron references remain programme-bounded:
  `NONE IDENTIFIED` ≠ `NONE EXISTS` (`M8-S12`).
