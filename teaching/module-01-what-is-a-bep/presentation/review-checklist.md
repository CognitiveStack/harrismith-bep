# Module 1 — Review Checklist

**Status:** For ChatGPT and the presenter, **after** the first PowerPoint is
assembled and **before** rehearsal.

Production checks that the deck was built correctly.
[`production-checklist.md`](production-checklist.md) covers that. **This
checklist asks whether the deck is any good**, and whether it is safe to say out
loud.

Work through the four sections in order. Rehearsal readiness is last because it
is meaningless if content or teaching review fails.

---

## 1. Content review

### 1.1 Accuracy

- [ ] Every factual claim traces to a source in
      [`../source-map.md`](../source-map.md)
- [ ] Quotations are verbatim, including the Slide 13 statement
- [ ] Section references in footers are correct
- [ ] Container, event and role names match the sources exactly
- [ ] Nothing asserts a project fact the sources record as unestablished

### 1.2 Completeness

- [ ] All ten Module 1 subjects are addressed across the fourteen slides
- [ ] The central teaching message is delivered, not merely implied
- [ ] The three honesty positions appear: training implementation · approved with
      conditions and not published · agreement is not implementation
- [ ] Nothing essential was lost in compression from the teaching source

### 1.3 Source traceability

- [ ] Each slide's evidence classification matches
      [`deck-specification.md`](deck-specification.md) §4
- [ ] Source notes appear where a claim is quoted, extracted or likely to be
      challenged
- [ ] A reviewer can get from any slide back to the controlled document behind it
- [ ] No claim is attributed to a document that does not make it

### 1.4 Terminology

- [ ] `Record / Retained` — and **`Archived` nowhere**
- [ ] *Lead Delivery Party* — never *lead appointed party* / *appointed party*
- [ ] **No RACI**
- [ ] Seven-term grammar correct where shown
- [ ] Check · Review · Authorise · Accept · Coordinate used precisely, not
      collapsed into "approval"

### 1.5 Management logic

- [ ] The argument runs problem → definition → agreement → operation →
      implementation → transfer, and each hinge is visible
- [ ] Slide 3's six actions genuinely structure what follows
- [ ] Slides 7 and 8 land the difference between allocation and commitment
- [ ] The deck reads as **BIM management**, not software operation

### 1.6 Teaching synthesis

- [ ] Slide 5's comparison is labelled and never attributed to a Harrismith
      document
- [ ] Slide 14's closing message is labelled synthesis
- [ ] Slide 3's six-verb framing is footnoted as teaching structure
- [ ] Slide 2's teaching statement is marked as teaching wording
- [ ] Labels are present where a misreading is likely — and **absent elsewhere**,
      so they stay visible

### 1.7 Unresolved matters

- [ ] Publication / exchange authority shown unresolved on Slides 8 and 10
- [ ] Recipient acceptance authority shown unresolved
- [ ] `TRN-E03` shown blocked with its reason indicated
- [ ] `T4` shown blocked, not completed
- [ ] Slide 5's unresolved panel present and honest
- [ ] **Nothing unresolved has been quietly resolved to make a slide look
      finished**

## 2. Visual review

### 2.1 Readability

- [ ] Every element readable at projection distance, not laptop distance
- [ ] Diagram labels legible without leaning forward
- [ ] Contrast adequate for a lit room
- [ ] Deck survives greyscale — dashed/solid distinctions do not depend on colour

### 2.2 Hierarchy

- [ ] Title dominant; main statement clearly second; supporting items clearly
      third
- [ ] The eye lands on the principal message first on every slide
- [ ] Footers recede — legible but never competing

### 2.3 Whitespace

- [ ] No slide feels crowded
- [ ] Margins consistent
- [ ] Diagrams have room around them
- [ ] Slide 14 in particular is not overloaded — if it is, the three takeaways
      become a fifteenth slide rather than being cut

### 2.4 Diagram complexity

- [ ] No diagram exceeds six to eight nodes
- [ ] Compressions preserved: Slide 11 shows six stages, not sixteen steps
- [ ] Nothing simplified to the point of changing governance meaning

### 2.5 Text density

- [ ] Roughly 40 visible words per slide, excluding diagram labels
- [ ] Slides 5, 7, 13 and 14 exceed it only because a comparison *is* the content
- [ ] No paragraphs; no dense extracts; no raw matrix, schedule or process list

### 2.6 Consistency

- [ ] Title treatment identical across fourteen slides
- [ ] Shapes, weights and colours mean the same thing throughout
- [ ] Table styling consistent
- [ ] Warning-label styling consistent

### 2.7 Misleading arrow or status implications — **the highest-risk visual check**

- [ ] **No arrow implies automation where human authority is required**
- [ ] **No completed chain where an authority is unresolved** — Slide 10
      especially
- [ ] Dashed elements still read as dashed at scale
- [ ] Slide 6 uses plain lines, not arrowheads — no contractual hierarchy implied
- [ ] Slide 14's final box reads as *not yet real*
- [ ] **No diagram could be mistaken for a live platform screenshot** — Slide 12
      especially

## 3. Teaching review

### 3.1 The project problem is clear

- [ ] Slide 2 lands as recognisable experience, not abstraction
- [ ] The audience would concede the problem exists on their own projects
- [ ] It does not read as blame

### 3.2 The definition is clear

- [ ] A non-BIM listener could restate what a BEP is after Slide 3
- [ ] The six actions are memorable and unnumbered
- [ ] The "is not" list defuses the common substitutes

### 3.3 Harrismith works as the worked example

- [ ] Used consistently — no example switching mid-deck
- [ ] Its status stated plainly rather than glossed
- [ ] Its gaps presented as **discipline**, not deficiency

### 3.4 BEP-to-supporting-document connection

- [ ] Slide 6 lands "one system, seven documents"
- [ ] The non-duplication reason is given, not just asserted
- [ ] Slides 7 and 8 visibly *are* the detail Slide 6 promised

### 3.5 Approval versus implementation

- [ ] Slide 13 separates all five states
- [ ] The quotation carries weight and is attributed
- [ ] The audience leaves able to ask "what evidence shows we're doing it?"
- [ ] It reads as the strongest slide, not an apology

### 3.6 Triviron transfer is useful

- [ ] The questions are genuinely actionable
- [ ] Each is recognisably derived from a Harrismith gap
- [ ] **No Triviron fact is stated**
- [ ] The audience leaves with work, not with a document

### 3.7 Suitable for a mixed audience

- [ ] A non-Revit listener follows the whole deck
- [ ] A commercially-focused listener finds something they care about
- [ ] A technical listener is not patronised
- [ ] Jargon is introduced only where it earns its place

## 4. Rehearsal readiness

**Rehearsal has not occurred and is not marked complete by this checklist.**
These items confirm only that rehearsal *can now begin*.

- [ ] Slides are understandable **without reading the notes** — the visual and
      title carry the message
- [ ] Presenter cues are concise fragments, not prose to be recited
- [ ] Transitions are available for every slide, and visible in the notes
- [ ] Likely questions and safe answers are to hand for all fourteen slides
- [ ] Time allocations are in the notes pane
- [ ] The 30-second opening, 30-second closing and 10-second closing fallbacks
      are available
- [ ] Section recovery cues are available for all six blocks
- [ ] The presenter knows which claims are teaching synthesis and can say so if
      challenged
