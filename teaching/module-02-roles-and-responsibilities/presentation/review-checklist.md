# Module 2 — Review Checklist

**Status:** For ChatGPT and the presenter, **after** the first PowerPoint is
assembled and **before** rehearsal.

[`production-checklist.md`](production-checklist.md) checks that the deck was
built correctly. **This checklist asks whether it is accurate, teachable and safe
to say out loud.**

Work the four sections in order. Rehearsal readiness is last because it is
meaningless if content or teaching review fails.

**Section 5 lists automatic fail conditions.** Any one of them is a fail — not a
"pass with observations".

---

## 1. Content review

### 1.1 Terminology

- [ ] Exact source terms used throughout — Owner / Appointing Party · Lead
      Delivery Party · BIM Manager · BIM Coordinator · Task-Team Lead · Author ·
      Checker · CDE Administration · Receiving / recipient function
- [ ] **`CDE Administration`** (function) distinguished from **`CDE
      Administrator`** (participant)
- [ ] `Task-Team Lead` hyphenated
- [ ] **No `lead appointed party` or `appointed party`** — neither appears in the
      sources
- [ ] **No RACI** in any diagram, legend, key, note or spoken answer
- [ ] The seven-term grammar quoted correctly where shown
- [ ] No generic stock role description substituted for a source term

### 1.2 Role boundaries

- [ ] BIM Manager duties **and** limitations both present, in balance
- [ ] The G4 nuance survives — the BIM Manager coordinates standards; the
      Task-Team Lead performs
- [ ] BIM Coordinator duties **and** technical boundary both present
- [ ] Coordination is process authority, not design ownership
- [ ] Task-Team Lead, Author and Checker remain three distinct functions
- [ ] CDE Administration implements and does not create governance

### 1.3 Authority accuracy

- [ ] Controlled sharing shown as the **established** authority, with the
      Task-Team Lead
- [ ] Publication / exchange shown **unresolved and blocked**
- [ ] Acceptance shown **unresolved or recipient-dependent**
- [ ] Governance change shown unresolved, by change class
- [ ] Implementation verification shown conditional — no universal verifier
- [ ] **Technical / design approval shown outside information-management
      authority**
- [ ] `Allocated` is not presented as contractually established
- [ ] **No universal approver** implied anywhere

### 1.4 Unresolved matters

- [ ] All three unresolved authorities visible on the deck
- [ ] Slide 12's simplified register retains every non-allocated row
- [ ] Slide 11's two unheld links are shown, not omitted
- [ ] Nothing unresolved has been quietly resolved to make a slide look finished

### 1.5 Evidence versus synthesis

- [ ] Teaching-synthesis statements identifiable — Slides 1, 6, 12, 13, 14
- [ ] Slide 8's message labelled as supported interpretation
- [ ] Slide 8's worked example labelled as the source's own educational
      illustration
- [ ] No claim attributed to a document that does not make it
- [ ] A reviewer can get from any slide back to the controlled source behind it

### 1.6 Function versus holder

- [ ] Function, organisation and named holder remain three distinct layers
- [ ] Every holder shown as TBD or not established
- [ ] No organisation shown as appointed
- [ ] TBD holders are **not** presented as invalidating the framework
- [ ] Documented functions are **not** presented as an operating system

### 1.7 Triviron

- [ ] **No Triviron organisation, person, date, requirement, platform choice or
      scope is asserted**
- [ ] Slide 14 contains questions only
- [ ] Stage 7 remains future-facing

## 2. Visual review

- [ ] **No vertical hierarchy on any slide**
- [ ] **BIM Manager not at the top** or otherwise visually distinguished as
      senior
- [ ] Slide 6's two columns carry **equal width and weight** — no greying, no
      smaller type, no "but…" framing on the right
- [ ] Slide 7 keeps each container labelled with its **originating task team**
- [ ] Slide 8 keeps the technical response visibly in the task-team lane, and
      responsibility visibly returns
- [ ] **Arrow semantics correct** — solid = allocation or governed progression;
      thick = derivation; plain = non-hierarchical relationship; **dashed =
      unresolved, blocked, future or unimplemented**
- [ ] **Unresolved links visible** on Slides 9, 11, 13, 14
- [ ] **Permission direction correct** on Slide 10 — one way, no return path
- [ ] **Slide 12 readable without removing unresolved rows**
- [ ] **Future states visibly future** — Slide 14 stage 7 has no tick, percentage
      or date
- [ ] Whitespace adequate; no slide feels crowded
- [ ] Dashed elements still read as dashed at projection distance
- [ ] Deck survives greyscale
- [ ] No diagram could be mistaken for a platform screenshot

## 3. Teaching review

- [ ] The audience understands **why roles must be explicit** — Slide 1 lands as
      recognisable experience, not abstraction
- [ ] **Role is distinguished from job title**
- [ ] **Function, organisation and person are distinguished**
- [ ] **The BIM Manager is neither universal authority nor weak administrator** —
      the "defined, not diminished" framing survives
- [ ] **The BIM Coordinator is not the designer**
- [ ] **Task-team separation of duties is memorable** — a listener could restate
      Author → Checker → Task-Team Lead → Shared afterwards
- [ ] **Access is separated from authority**
- [ ] **The "final approver" misconception is corrected** — a listener would not
      leave looking for one
- [ ] **The Triviron assignment questions are practical** — actionable, and
      recognisably derived from Harrismith gaps
- [ ] A non-BIM listener follows the whole deck
- [ ] A commercially-focused listener finds something they care about
- [ ] A technical listener is not patronised

## 4. Rehearsal readiness

**Rehearsal has not occurred and is not marked complete by this checklist.**
These items confirm only that rehearsal *can now begin*.

- [ ] Slides are understandable **without reading the notes**
- [ ] Presenter cues are concise fragments, not prose to be recited
- [ ] Transitions available for every slide and visible in the notes
- [ ] Likely questions and safe answers to hand for all fourteen slides
- [ ] Time allocations in the notes pane
- [ ] 30-second opening, 30-second closing and 10-second closing fallbacks
      available
- [ ] Recovery sentences available for all eight blocks
- [ ] The presenter knows which claims are teaching synthesis and can say so if
      challenged

## 5. Automatic fail conditions

**Any one of these is a fail. Not "pass with observations".**

| # | Condition |
|---|---|
| 1 | **A fabricated holder or organisation** — including a name-shaped placeholder |
| 2 | **A hidden unresolved authority** — omitted from a diagram or cut from Slide 12 for space |
| 3 | **A vertical hierarchy** on any slide |
| 4 | **Permission represented as authority** — including a reversed or bidirectional Slide 10 arrow |
| 5 | **The BIM Coordinator shown designing the fix** |
| 6 | **Technical approval placed inside information-management authority** |
| 7 | **A complete Shared → Published route** |
| 8 | **A completed Triviron implementation** — any tick, percentage or date on stage 7 |
| 9 | **An unsupported ISO or Triviron fact** |
| 10 | **A fabricated project screenshot** or any platform image |

Each of these is a claim the module spends twenty minutes arguing against.
Shipping a deck that commits one would undo its own case.
