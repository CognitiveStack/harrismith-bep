# Module 2 — Visual Demonstration Plan

**Status:** Candidate visuals for the whole Module 2 presentation. **Nothing is
prepared and no asset exists.** Every entry is a proposal.

**No live Autodesk observation is required in T2-A**, and none is requested.
Where an entry notes a possible future observation, that is an observation of a
possible need — **not an authorisation**. The safety boundary in root
[`README.md`](../../README.md) §2.1 applies unmodified.

---

## 1. How to read this plan

| Field | Meaning |
|---|---|
| **Slide / topic** | Where it is used |
| **Teaching purpose** | The one thing the audience should take from it |
| **Repository evidence** | The controlled source behind it |
| **Classification** | `DIRECT` · `INTERPRETATION` · `SYNTHESIS` |
| **Simplify** | What must be compressed |
| **Omit** | What must not reach the slide |
| **Overclaim risk** | The risk of asserting more than the sources support |
| **Live observation** | Whether a later bounded read-only observation would add value |

**Standing rule carried from Module 1:** a dense screenshot of a controlled
document is not a visual. Extracts are cropped to the rows that carry the
message.

**Module-specific standing rule:** **no visual may name a person or an
organisation.** Every role holder is TBD, and no organisation is appointed.

## 2. Candidate visuals

### R1 — Function versus person

| Field | Value |
|---|---|
| **Slide / topic** | Slides 2, 3 |
| **Teaching purpose** | Separate the function from the label and from the human — and show that one person may carry several functions without merging them |
| **Repository evidence** | BEP §4.6, §5.11 |
| **Classification** | **DIRECT** — "These are functions, not job titles and not people" |
| **Simplify** | Two or three functions maximum, one participant figure. The §5.11 example — approving as BIM Manager, applying as CDE Administrator — is the whole visual |
| **Omit** | Any name, any job title, any photograph or avatar, any org-chart shape |
| **Overclaim risk** | **Low.** Guard only against a figure that reads as a specific person |
| **Live observation** | No |

**Design note.** Avoid a human silhouette if it invites "who is that?". A neutral
labelled container carrying two function badges works better.

### R2 — Three-layer model: function · organisation · named person

| Field | Value |
|---|---|
| **Slide / topic** | Slide 3 |
| **Teaching purpose** | Show three layers, with Harrismith's third deliberately empty |
| **Repository evidence** | BEP §4.2, §4.6, §5.2; IM matrix §2 |
| **Classification** | **INTERPRETATION** — the layers are sourced individually; the three-layer stack is teaching structure |
| **Simplify** | Three bands. Populate band 1 with the four IM functions, band 2 with party *categories*, band 3 with `TBD` |
| **Omit** | Any name in band 3; any company in band 2; the full nine-role matrix |
| **Overclaim risk** | **Medium.** A tidy three-band diagram implies the third band is merely pending. It is unresolved, and the slide must not suggest a date |
| **Live observation** | No |

**Requirement.** Band 3 is drawn visibly empty — dashed or outlined — not filled
with placeholders. Placeholders read as names.

### R3 — Role-boundary diagram

| Field | Value |
|---|---|
| **Slide / topic** | Slides 5–8 |
| **Teaching purpose** | Show each function's edge — what it holds and what it does not |
| **Repository evidence** | BEP §5.4–5.9; IM matrix §4 ("Role principles preserved" — a **Holds / Does not hold** table); Coordination Strategy §3 |
| **Classification** | **DIRECT** — the matrix §4 table is exactly this shape |
| **Simplify** | Two roles per slide at most. Two columns: *holds* / *does not hold*, three rows each |
| **Omit** | All eight rows of matrix §4 at once; any holder name |
| **Overclaim risk** | **Low** — the source table is already a boundary statement |
| **Live observation** | No |

**This is the highest-value repository-derived visual in the module.** IM matrix
§4 is a ready-made boundary table for eight roles and needs cropping, not
redrawing.

### R4 — Role-and-authority map

| Field | Value |
|---|---|
| **Slide / topic** | Slide 12 |
| **Teaching purpose** | The whole model on one slide: which function holds which authority, and which authorities nobody holds |
| **Repository evidence** | IM matrix §3.1–3.7 and §6; BEP §9.7, §9.8, §12.7 |
| **Classification** | **DIRECT** for each allocation; **INTERPRETATION** for the consolidated view |
| **Simplify** | **Six authorities maximum**, not sixteen. Author · Check · Authorise share · Coordinate · Publish · Accept |
| **Omit** | The full nine-column grid; all 25 process functions; any RACI letter |
| **Overclaim risk** | **High if the unresolved ones are omitted.** Publication and acceptance must appear, visibly unheld |
| **Live observation** | No |

**Requirement.** Unresolved authorities are shown as **empty holders** — a
labelled authority with no function attached — not omitted. An authority absent
from the diagram reads as an authority that does not exist.

### R5 — BIM Manager: does / does not automatically do

| Field | Value |
|---|---|
| **Slide / topic** | Slides 5, 6 |
| **Teaching purpose** | The module's principal boundary |
| **Repository evidence** | BEP §5.5; IM matrix §4; Coordination Strategy §3 |
| **Classification** | **DIRECT** — both columns are source lists |
| **Simplify** | Five *does* rows, five *does not automatically* rows |
| **Omit** | The full nine-item responsibility list from §5.5; the AG-series governance functions |
| **Overclaim risk** | **Low in content; moderate in tone.** The right column can read as diminishing the role |
| **Live observation** | No |

**Design note.** Give both columns equal visual weight. A smaller "does not"
column reads as a caveat; it is half the teaching.

### R6 — BIM Coordinator workflow

| Field | Value |
|---|---|
| **Slide / topic** | Slides 7, 8 |
| **Teaching purpose** | Show the coordination function as process authority, ending at verification — **not** at design approval |
| **Repository evidence** | BEP §5.6; Coordination Strategy §3, §16, §19; IM matrix §3.5 |
| **Classification** | **DIRECT** |
| **Simplify** | Five steps: organise inputs → federate → triage → coordinate assignment → verify disposition. Terminate the chain visibly at *verify* |
| **Omit** | The sixteen-step cycle (Module 6); any Navisworks or Model Coordination screenshot; any clash count |
| **Overclaim risk** | **High.** A coordination chain implies a running process. The sources record that **no Design Collaboration Coordination Space was observed configured** and the status model is **not claimed to be configured** |
| **Live observation** | **Possibly later**, but see the overclaim risk. Platform imagery would compound rather than illustrate |

**Requirement.** The chain must visibly stop at *verify*, with design approval
shown **outside** it. Coordination Strategy §3: the Coordinator does not own
discipline design solutions, become technical approver, or acquire publication
authority through coordination.

### R7 — Task team: author / check / authorise

| Field | Value |
|---|---|

| **Teaching purpose** | Three functions, one container, three different people-or-acts — and **the Author does not self-authorise** |

**This is the module's anchor visual.** It is the one place the whole separation
becomes concrete, and Slide 9 has the longest allocation because of it.

**Second panel, if space allows:** Author and Checker combined — the functional
distinction remains, the combination is **recorded**, and *"independence is never
claimed where it does not exist."*

### R8 — CDE Administration versus governance authority

| Field | Value |
|---|---|
| **Slide / topic** | Slide 10 |
| **Teaching purpose** | Permission and authority as separate, non-derivable concepts |
| **Repository evidence** | BEP §5.9, §6.9, §1.5; CDE Strategy §14, §17; IM matrix §3.2 C2/C3 note |
| **Classification** | **DIRECT** |
| **Simplify** | Two boxes, one arrow. **Authority → permission**, never the reverse |
| **Omit** | **Any Autodesk permission-settings screenshot**; any folder tree |
| **Overclaim risk** | **Low if the arrow direction is right; high if reversed or bidirectional** |
| **Live observation** | **No — actively counterproductive.** A permissions view invites the inference the slide refutes |

**Carried from Module 1's `M01-S10`**, which solved the same problem. Reuse the
approach: authority and permission drawn as non-touching concepts with a single
directional arrow.

## 4. Standing cautions

1. **No live Autodesk work is authorised by this plan**, and none is requested in
   T2-A.
2. **No visual names a person or an organisation.** Every holder is TBD; no party
   is appointed.
3. **Unresolved authorities are drawn, not omitted** — R4, R9 and R10 depend on
   it.
4. **No RACI terminology** in any diagram, legend or label.
5. **No ISO role terminology** — `lead appointed party` and `appointed party`
   appear nowhere in the sources.
6. **Extracts inherit their source's status.** All sources are approved with
   conditions and **not published**.
7. **No final assets are created in T2-A.**
