# Presentation Principles

**Status:** Working rules for the teaching programme. **Not governance.**

These apply to every module. They are initial rules, established with Module 1,
and are expected to be revised as delivery experience accumulates.

---

## 1. Teach through a project problem and its resolution

Start with a situation the audience recognises, then show how the agreement
resolves it. Never open with a definition — a definition offered before the
problem is felt is heard as jargon, and the audience spends the rest of the talk
waiting for the relevance.

The order is: **problem → resolution → mechanism → transfer.**

## 2. Use Harrismith as the concrete worked example

Every abstraction is illustrated on the same project. One coherent example
carries more than five disconnected ones, because the audience builds a mental
model of the project and each new point attaches to it.

Do not switch examples mid-talk to make a point land more easily. If Harrismith
cannot illustrate something, say so — that is useful information about the
example's limits.

## 3. Distinguish BIM Management from software operation

This is the distinction the programme exists to teach, and it is the one the
audience is most likely to collapse.

| Software operation | BIM Management |
|---|---|
| How to share a model in Design Collaboration | Who is permitted to authorise that share, and for what purpose |
| How to run a clash test | What a finding is, when it becomes a tracked Issue, and who verifies its resolution |
| Where a file sits in the folder tree | What state the information is in, and what it may be relied on for |

Software appears as the environment in which managed information moves. It is
never the subject. **A platform permission is not authority** (BEP §1.5, §5.9) —
this is the sharpest available statement of the distinction, and it is worth
using directly.

## 4. One principal message per slide

If a slide has two messages, it has none — the audience picks one, and not
reliably the one intended.

Test: state the slide's message in a single sentence. If the sentence needs an
"and", split the slide.

## 5. Diagrams, extracts and model views — not dense document screenshots

A projected page of a controlled document is not a visual. It is a wall of text
the audience reads instead of listening, and it cannot be read at projection
size anyway.

| Instead of | Use |
|---|---|
| A screenshot of a full section | The one table in it that carries the message |
| A full nine-column matrix | The four rows that make the point |
| A sixteen-step process list | A redrawn loop with five or six labelled stages |
| A full federated model | Two or three disciplines at one interface |

Several of the source documents contain sequences that are already
diagram-shaped in text — the CDE transition routes and the coordination cycle in
particular. Redraw them; do not screenshot them.

## 6. Separate agreed governance from evidence of implementation

Agreement and implementation are different states, and conflating them is the
most consequential error available in this subject.

| State | Is | Evidence |
|---|---|---|
| **Proposed** | Drafted for consideration | The document itself |
| **Approved** | Decided through the governance route | The recorded decision |
| **Implemented** | Operating in the project | The acts themselves — checks, authorisations, transitions, deliveries |

A presentation that shows an approved document and implies a running process
misrepresents it. Say which state is being shown. For Harrismith the honest
statement is: **approved with conditions, publication not authorised, not
issued** — and saying so is the strongest thing in the talk, not the weakest.

## 7. Introduce ISO terminology only when it clarifies the practical workflow

Terminology is introduced when it makes a workflow easier to describe, and not
otherwise. "Information container" earns its place because "file" is wrong and
"model" is too narrow. Others do not, in a first presentation.

Two constraints:

- **No compliance is claimed.** ISO 19650 principles inform the Harrismith
  approach; that is a statement of influence and nothing more (BEP §13.4). Never
  imply certification, assessment or compliance.
- **Do not attribute wording to a standard unless verified.** The repository
  reproduces no standards text. Where a term is used in a practical sense that
  may differ from the strict standard definition, say so — see
  [`glossary.md`](glossary.md) section 3.

## 8. Translate concepts into future Triviron decisions

Every module ends by converting what was taught into decisions a Triviron
project would have to take. This is what makes the programme preparation rather
than appreciation.

The translation is always in the form of **questions Triviron must answer**,
never assertions about Triviron. No Triviron project information exists in this
repository, and none may be invented.

## 9. Notes support natural delivery, not word-for-word reading

Speaker notes distinguish four things: the **essential message** that must be
communicated, **suggested wording** as one route to it, a **shorter fallback**
for time pressure, and the **transition** to what follows.

Suggested wording is written to be reacted against. If it does not sound like
the presenter, it should be replaced — that is the notes working as intended, not
failing.

Read the essential message before delivery. Do not read the wording during it.

---

## 10. Two working rules that follow from the above

**Say what is not known.** Harrismith's gaps — no appointing party, no
information requirements, no established standards, an unresolved team-space
mapping — are teaching material, not embarrassments. A documentation set that
records what it does not know is demonstrating the discipline being taught.

**Do not defend the example.** When someone challenges Harrismith's status,
agree with the accurate part of the challenge. It is a training implementation;
it is not issued; it is not evidence of a running process. Conceding this costs
nothing and buys the credibility that the rest of the talk runs on.
