## 2. Module-wide visual rules

### 2.1 Status must be visible

**Every visual that shows governance, implementation, an allocation, a decision,
a status, a transition, a cycle or an observed fact must display the applicable
status in words, on the slide.**

**Status may never exist only in the presenter notes.** **Status meaning may
never depend on colour alone.** Every status is carried by a **word**.

The status vocabulary available to Module 6 visuals:

| Status | Used where |
|---|---|
| `CONTROLLED GOVERNANCE` | Explicit BEP §8 or §9 wording |
| `PROPOSED GOVERNANCE` | `S2` content unless expressly classified otherwise; `S3` allocations |
| `APPROVED WITH CONDITIONS — Training Baseline 0.1` | The four principal resources, under `AD-001` |
| `PUBLICATION NOT AUTHORISED` | The document status carried by `AD-001` |
| `UNRESOLVED` | Publication authority, acceptance authority, `A2`, `A4`, decision owners, the coordination environment |
| `BLOCKED` | `T4`; `TRN-E03` |
| `TBD` | Every one of the twelve check tolerances or rules |
| `OPEN` | `GCR-006` |
| `IMPLEMENTATION UNVERIFIED` | An allocation not checked against the live environment |
| `OBSERVED — QUALIFIED` | `OF-002`, `OF-005`, `OF-007`, `OF-008` at the inspected level |
| `PARTIALLY TRACEABLE` | The cycle, per `S8` §8 |
| `NOT DEMONSTRATED` | Looked for and not established — **never a failure claim** |
| `NOT ESTABLISHED` | The assurance-sampling method (`U14`); whether verification is mandatory in every cycle (`H18`); the suitability code set |
| `NOT YET ESTABLISHED` | Triviron; **every Slide 14 answer area** |

**No new status may be invented for visual convenience**, and **no visual is
required to use every status**. Each specification names the ones it must carry.

### 2.2 Reference canvas

| Parameter | Requirement |
|---|---|
| Canvas | **960 × 540 pt**, 16:9 |
| Origin | Top left; `x` increases right, `y` increases down |
| Title zone | **`y = 0–72` — reserved.** No content beneath the title baseline |
| Side margins | **≥ 48 pt** |
| Minimum visible type | **14 pt** |
| Principal labels | **≥ 18 pt** |
| Text contrast | **≥ 4.5 : 1** |
| Border and connector contrast | **≥ 3 : 1** |

**Geometry varies by slide.** Every specification states enough spatial
relationship to prevent semantic drift: **relative position · equal or unequal
visual weight · separation · adjacency · reading order · which objects may
connect · which objects must never touch or merge.**

### 2.3 External imagery

**External imagery: `NONE REQUIRED` — for all fourteen visuals.**

Prohibited throughout: stock photographs · Autodesk, ACC, Forma, Revit or
Navisworks screenshots · live platform screenshots · model screenshots · company
logos · Autodesk logos · observed folder screenshots · interface captures ·
downloaded diagrams · external icons where a native shape can carry the meaning.

**Why.** A platform image makes implementation look concrete, while Module 6
records at Slides 3, 4, 6, 7, 9, 10, 11, 12 and 13 that **a complete governed
coordination cycle has not been demonstrated** and that **`GCR-006` remains
OPEN**. An interface picture asserts operation more persuasively than any caption
can withdraw it.

### 2.4 Live evidence

**Live evidence: `NONE REQUIRED` — for all fourteen visuals.**

**No new observation is needed, and none is authorised.** The existing
observations — `OF-002`, `OF-005`, `OF-007`, `OF-008` and `S8` — appear **only as
bounded text carrying their accepted qualification**. **No simulated platform
screenshot may be produced**, because a simulation of an unauthorised observation
is worse than the observation.

### 2.5 Visual form

**Default and expected form: `Native PowerPoint-reconstructable layout`.**

Permitted: rectangles · text boxes · simple tables · native warning strips ·
simple labelled connectors · unfilled checklist boxes · deliberately incomplete
grids · native call-outs.

Prohibited: **SmartArt** · imported infographics · **Mermaid** · automatic
diagram layouts · automatic process diagrams · decorative three-dimensional
effects · software-interface replicas.

**Mermaid risk test — applied separately to every visual.** A Mermaid or
auto-layout form is prohibited wherever automatic graph layout could falsely
imply **hierarchy · ownership transfer · a completed cycle · an automatic Issue ·
a mandatory status sequence · an approved tolerance · verification in every
cycle · closure as proof · a Triviron answer.**

**Result: `Mermaid PROHIBITED` for all fourteen.** Every Module 6 visual carries
at least one of those hazards, and most carry several. **No Mermaid form is
proposed anywhere in this module.**

### 2.6 Accessibility

Every specification carries: **logical reading order · a screen-reader
description · status meaning in words · no information by colour alone · the
minimum type requirements of §2.2 · a projection-readability warning · connector
meaning carried by direction and label rather than colour · warnings that remain
legible at projection size · an alternative verbal description of the visual's
principal relationship.**

**Anything a sighted reader takes from separation, enclosure, weight or position
must also be said in words**, because none of those survive audio.

### 2.7 Visual economy

**The accepted slide copy is content-complete. Much of it is too dense to
reproduce visually.** Each specification therefore identifies:

- **the principal visible relationship** — the one thing the layout must carry;
- **what may be abbreviated** — usually definitions and examples;
- **what must remain verbatim** — controlled quotations, status words, the
  qualifiers `as applicable`, `required`, `material`, `where established`,
  `only where genuinely established`;
- **what belongs only in speaker notes**;
- **what may be grouped**;
- **what must never be compressed** — every load-bearing distinction, count and
  status.

**A specification must not attempt to put every source sentence on the slide.**
**It must preserve every load-bearing distinction and status.**
