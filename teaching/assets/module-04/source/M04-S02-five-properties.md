## 1. Purpose and five-second takeaway

Show **five properties answering five different governance questions**, all describing one container **at the same time**.

**If the audience takes one thing from this visual in five seconds:**

> One container has all five at once. They are not stages.

## 2. Source and authority basis

`S1` §6.8 defines all five and supplies the sentence the visual is built around: **a new platform version creates none of the others.** `S2` §13 adds the rule — *"these are never used interchangeably"*.

**Revision carries a conditional in its own controlled definition** — *"a controlled issue identifier, **where project convention requires one**"* — and `S1` §11.3 with `S12` records that **no project naming or revision convention has been established**. The property is defined; **its code set is not.**

**State and Version are different.** State is a governed concept (`S1` §6.3). Version is *"a platform or file history instance"* — platform-native, with no project convention required. **Neither has an unestablished project code set**, and neither may be labelled as though it did.

## 4. Fixed layout

**Five equal cards in one row.** One property per card, one question per card, one code-set line per card. Nothing else on a card.

**The three-plus-two grid is rejected and is not an alternative.** Recorded here so it is not silently reopened during production:

- unequal rows imply that three properties group together and two are a remainder;
- a two-row layout adds a **second reading direction** to a visual whose entire purpose is to have none.

At the fixed geometry each card carries a four-word property name and a six-word question at 16 pt without compromise, so the readability condition that would have justified the grid **does not arise**.

**The fixed form, carried from the `W2` specification:**

## 7. Connector semantics

**Not applicable — no connector, by requirement.**

No arrow, line, rule, bracket, progression bar, chevron, numbered step or connecting stroke may appear **between, above or beneath** the cards.

**The caption is set as free text with no rule under it** — a full-width rule above a row of cards reads as a spanning connector.

`S1` §6.8 is explicit: *a new platform version creates none of the others*. **Any drawn relationship contradicts the governing source.**

## 8. Status and warning treatment

The three `established` negatives sit **on their own cards**, as the card footer, at the same level on every card.

**They are not collected into a footnote.** A footnote reads as a caveat about the slide; a line on the card reads as the project's position on that property.

**State and Version must not acquire a *not established* label.** Marking all five uniformly would invent an unresolved matter the sources do not record.

## 9. Build or reveal sequence

**Not applicable — no build. All five cards appear together, in a single frame.**

A staged reveal teaches sequence no matter what the presenter says over it, and **this is the one visual in the module where the reveal itself would carry the error.**

## 10. Mandatory omissions

No filename · no revision code · no status code · no suitability code · no metadata field set · no maturity level · no progress indicator · no approval tick · no traffic-light or red-amber-green treatment · no folder path · no numbering on the cards · **no metadata as a sixth card** · no ISO attribution — these are this project's definitions, not ISO definitions.

## 11. Accessibility and projection requirements

- **All five cards carry equal semantic weight**, and are marked up as peers — not as a list with a first item, and not as a table with a header row.
- **No meaning depends on card colour or fill.** If cards are tinted, all five are tinted identically. The three *not established* lines are text.
- **Consistent heading hierarchy**: property name is the card heading, question is body, code-set line is a footer at the same level on every card.
- **Separation ≥ 21 pt** between cards so they cannot merge visually into a process chain; card border contrast ≥ 3:1.
- **Type: property name 20 pt, question 16 pt, code-set line 14 pt minimum.** Questions wrap to a maximum of three lines at 156 pt.
- **Contrast ≥ 4.5:1** for all text.

## 12. Screen-reader or presenter-notes description

> One caption and five cards of equal size, side by side, **with nothing drawn between them**. Caption: one information container — all five at once. Card one, State: where may it be used? A governed concept. Card two, Version: which stored occurrence is this? Platform-native; no project convention. Card three, Revision: which managed issue is this? No convention established. Card four, Status: what condition is declared? No code set established. Card five, Suitability: for what use is it suitable? No code set established. Beneath: a new platform version creates none of the others — source, project BEP section 6.8. **The cards are not in an order and are not connected.**

## 13. Producer-failure test

The visual fails if a viewer can reasonably read it as:

- five **sequential stages**;
- one property **automatically causing** another;
- a **code standard**;
- a **progression toward approval**.

## 14. STOP conditions

**Stop production and return to the `W2` specification if:**

- an arrow, rule, bracket or connecting line appears anywhere in the card row;
- a card becomes visually dominant, or the cards become unequal;
- an example code, filename or field name is added to any card;
- a maturity, progress or completion grammar appears;
- **metadata is added as a sixth card**;
- State or Version acquires a *not established* label;
- **the row is rebuilt as a three-plus-two grid** — the single-row form is a recorded decision, not a default.
